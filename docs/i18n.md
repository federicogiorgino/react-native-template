# Internationalization (i18n)

Files: `src/lib/i18n/index.ts`, `en.ts`, `it.ts`, `src/app/(settings)/language.tsx`. Built on [i18next](https://www.i18next.com) and `react-i18next`, with `expo-localization` to read the device language.

The app ships English and Italian. It follows the device language by default, and users can override it in Settings → Language. The choice is saved on the device.

## Using translations

In a component:

```tsx
import { useTranslation } from "react-i18next";

export default function Example() {
  const { t } = useTranslation();
  return <Button.Label>{t("common.cancel")}</Button.Label>;
}
```

With values:

```tsx
t("home.greeting", { name: session.user.name }); // "Hi, {{name}}"
t("validation.passwordMin", { count: 10 }); // "Use at least {{count}} characters."
```

Outside React (API helpers, plain modules), use the shared instance:

```ts
import { i18n } from "@/lib/i18n";

i18n.t("errors.network");
```

Keys are type checked: `t("common.cancell")` fails typecheck, and your editor autocompletes keys. Dynamic keys must be built from known literals, for example ``t(`theme.${preference}`)`` where `preference` is `"system" | "light" | "dark"`.

Rules:

- Never write user-visible text in a component. That includes button labels, titles, placeholders, empty states, toasts, alerts and `accessibilityLabel`s.
- Do not build a sentence from several keys. Word order differs between languages, so use one key with `{{values}}`.
- Do not translate server error messages. Show them as received; the app's own error messages (network, timeout, 401...) are translated.
- Names of languages are shown in their own language (`English`, `Italiano`), so they are not translated.

## Adding a string

1. Add the key to `src/lib/i18n/en.ts`, in the group for that screen or feature.
2. Add the same key to `src/lib/i18n/it.ts` (and every other language). Typecheck fails until every language has it.
3. Use it with `t("group.key")`.

Group names mirror screens (`auth`, `settings`, `account`...), with shared text in `common`, `validation` and `errors`.

## Adding a language

1. Create `src/lib/i18n/es.ts` (for Spanish) typed as `Translation`:

   ```ts
   import type { Translation } from "./en";

   export const es: Translation = {/* copy en.ts and translate every value */};
   ```

2. Register it in `src/lib/i18n/index.ts`:

   ```ts
   export const LANGUAGES = {
     en: { label: "English" },
     it: { label: "Italiano" },
     es: { label: "Español" },
   } as const;
   // and in init(): resources: { en: {...}, it: {...}, es: { translation: es } }
   ```

The language picker lists everything in `LANGUAGES` automatically. The device language is matched by its two-letter code; anything unsupported falls back to English.

## Forms

Validation messages are translated by building schemas from `t`:

```ts
const createSchema = (t: TFunction) =>
  z.object({ email: emailField(t), name: requiredText(t("validation.nameRequired")) });

const form = useForm({ resolver: zodResolver(createSchema(t)) });
```

See [forms-and-feedback.md](forms-and-feedback.md). Errors already shown stay in the old language until the field is validated again.

## Native pieces

- **System dialogs** (permission prompts) use the device language automatically.
- **App name on the home screen** is not translated by this setup. Per-language names need `locales` entries in `app.config.ts` and a strings file for each language; add them when you localize the store listing.
- **Dates, numbers and currency:** format with `Intl` (`new Date().toLocaleDateString(i18n.language)`, `Intl.NumberFormat(i18n.language)`) instead of hand-built strings.
- **Right-to-left languages** (Arabic, Hebrew) need extra layout work and an app restart when the direction changes; this template does not set that up.

## Testing

Set the device or simulator to another language, or use Settings → Language. Check long languages (German, Finnish) for text that overflows buttons and the tab bar, and test with larger system font sizes.
